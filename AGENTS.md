# AGENTS.md

## Overview

**unPawse** is a cat-themed **screen-time manager**: when an app's daily time limit is reached, the user must photograph their cat (verified on-device) to earn more time.

**The core loop works end-to-end**: pick apps and limits → a foreground service tracks real usage → hitting a limit draws a block over the offending app → photographing a verified cat credits bonus minutes and lets you back in → Home/Stats/Gallery render that real data. Every screen is backed by a real ViewModel + repository; `SampleData` survives only for the Block Overlay's in-app debug route. Screens stay stateless `XxxScreen(state, callbacks)`, so state can be re-sourced without touching them. What's left is polish and the gaps listed under **Current State**.

The design system ("Warm Minimalist") centers on a blush-pink (`#F5B6C8`) / plum (`#815060`) Material 3 palette over a warm-white surface, Inter-style typography, 24dp rounded cards, pill buttons, and a "squishy" 98%-press-scale feel. Source tokens live in the mockup's `DESIGN.md`.

## Architecture & Conventions

- **Dependency injection: manual, app-scoped.** `UnPawseApplication` builds a single `AppContainer` (`data/AppContainer.kt`) that owns the Room `CaptureDatabase` singleton, the shared `CaptureRepository`/`PhotoStorage`, the `SettingsRepository`, and derived app-wide state (e.g. `catDetectorMinConfidence`). ViewModel `factory(context)` methods read dependencies from it via `context.appContainer()` — they no longer rebuild the graph each time. `AppContainer` is an interface (`DefaultAppContainer` is the production impl) so tests can supply fakes. This is deliberately **not** Hilt/Koin — it keeps the "no extra compiler plugins" stance; the container is the seam a framework would later replace.
- **Data layer / repositories.** Each store follows the `CaptureRepository` pattern: one class exposes `Flow`s + `suspend` writers so callers never touch Room/DataStore directly. Room stack lives per-feature package: `@Entity` + a separate domain model + an `internal fun …toDomain()` mapper + `@Dao` returning `Flow`. There is **one database** — `CaptureDatabase` (historic name; now app-wide, holding `captures` + `monitored_apps` + `daily_usage`), reached via `getInstance()` and owned by the container. Pre-release schema changes bump `version` and rely on `fallbackToDestructiveMigration`; add real `Migration`s + `exportSchema = true` before shipping.
- **Usage tracking.** `UsageRepository` (`data/usage/`) is the source of truth for *what* is monitored (`monitored_apps`: package, label, `dailyLimitMinutes`, `enabled`) and *how much* has been spent (`daily_usage`, composite key `(packageName, date)` — a new day is a new row, so **daily reset is free**). Usage is stored in **seconds** for precision (the foreground monitor accrues sub-minute ticks) and exposed in minutes. Accrual goes through `@Transaction` DAO helpers that insert-if-absent then `+=`, so it's atomic. Limit arithmetic lives in pure, unit-tested functions (`UsageMath.kt`: `remainingSeconds` / `remainingMinutes` / `isLimitReached`), and reward-policy arithmetic beside it in `RewardPolicy.kt` (`decideReward` / `earnableMinutes`). The repository takes an injectable `today: () -> LocalDate` so rollover is testable and midnight-safe (each call re-reads it), plus a `now: () -> Long` for the reward cooldown.
- **UI state:** every screen is a stateless `XxxScreen(state: XxxUiState, …callbacks)` with an `XxxUiState.sample()` kept **for `@Preview` only**. Each live screen adds a stateful `XxxRoute` that owns a `ViewModel` (built by `XxxViewModel.factory(context)`) and collects `uiState` with `collectAsStateWithLifecycle()`. Every screen now follows this except the Block Overlay, whose state is *pushed in* (the service constructs `BlockUiState.forApp(label)`), so it has no ViewModel. Keep non-trivial mapping in pure, testable top-level functions (`toHomeUiState`, `toStatsUiState`, `toGallerySections`, `toAppLimitItems`, `classify`) — the ViewModel should only wire flows together.
  - ViewModels that mostly reshape one screen's data may use `XxxUiState.sample().copy(...)` as a base so the not-yet-real fields keep their mockup copy in one place. **This is only OK for *copy*, never for metrics** — see the Stats note below. It is a scaffold for a screen still being built, not a destination: **`SettingsMapper` and now `StatsMapper` both construct their state field by field**, with the handful of genuine constants (the MON–SUN axis, the donut's "Budget left" caption) as private `val`s in the mapper. Once every field on a screen is computed, inheriting from `sample()` buys nothing and leaves a standing route for mockup data to reach the screen the moment someone adds a field and forgets to set it. `StatsUiState.sample()` and `SettingsUiState.sample()` are now both `@Preview`-only.
- **Don't ship invented numbers.** `StatsMapper` blanks any metric with no feature behind it rather than inheriting `sample()`'s figures: a fabricated "42 interruptions prevented" sitting beside real ones reads as fact. A test pins this. Restore each only when the feature behind it exists. **Nothing on Stats is blanked any more** — `preventedCount`, `unlocks` and `achievements` have all graduated to real features (see the `blockedCount`, `data/unlocks/` and achievements notes under Architecture). The *rule* stands and is what matters: a metric with no feature behind it gets blanked, never inherited from `sample()`. Placeholder *copy* (greeting, banner, next-break countdown) is fine and is flagged in the mappers.
  - **A restored metric must also state its period.** The mockup's "Prevented / 42" said nothing about what it counted. It now counts the **Mon–Sun week** and the card says "THIS WEEK" on its face — the same week the chart draws and the trend compares, extending the rule below to a third card.
  - The same trap catches **mockup affordances that were never wired to state**. When a card's icon, colour, direction or *size* encodes a claim, it needs a state field like any other number. Three instances have been found and fixed, all in `StatsScreen`, and they are worth reading as a set because each survived a pass that was looking for fabricated *numbers*:
    1. The **trend arrow** was hardcoded to `TrendingDown` (the mockup's value was "-5.2h"), so a week where usage *rose* rendered "+0.6h" beside a downward arrow. Now driven by `StatsUiState.trendIsUp`.
    2. The **vs-yesterday arrow** was hardcoded to a green `ArrowDownward`, so a day where usage doubled rendered "100% from yesterday" as though it were an improvement. `deltaIsPositive` had existed and been tested the whole time — it was simply never read. Now drives both the arrow and its tint (`error` vs `secondary`), and the icon has a real `contentDescription` because it is no longer decorative.
       - **And the sequel, which is the more interesting half:** wiring the arrow to state produced a *new* wrong claim on a first day. `deltaIsPositive` is `todaySeconds > yesterdaySeconds`, and any usage at all beats zero, so a fresh install rendered a red upward arrow beside "No data for yesterday" — a direction against a baseline that doesn't exist. Caught on an emulator screenshot, not by a test. `deltaHasBaseline` now gates the icon, and the answer was to draw **no arrow**, not to pick a default: **a two-state field cannot express "there is nothing to compare".** Same shape as the theme override's tri-state, where a two-position `Switch` made "follow system" unreachable.
    3. The **donut arcs** came from a `UsageCategory.durationWeight()` table returning the mockup's literal 72/45/32 keyed off the *palette slot*, so every slice was drawn at a constant proportion regardless of the duration printed beside it in the legend. `UsageCategory` now carries `seconds` alongside its formatted `duration`, and `DonutChart` normalises those directly. **A formatted string is not a value** — any component that has to size something needs the number, not the label.
  - The empty "Recent Achievements" heading is likewise hidden rather than rendered over blank space — a bare heading reads as content that failed to load.
  - **Chart and trend must agree on what "this week" means.** Both now use the Mon–Sun calendar week; the trend previously summed rolling 7-day windows, so on a Monday it counted days the chart didn't draw and reported a rise next to a visibly flat week.
- **Settings persistence.** `SettingsRepository` (Preferences DataStore) persists the dark-mode override, cat-detection sensitivity, display name, daily-summary toggle, earned-minutes-per-cat, photo retention window, warning threshold, and reminder interval. `SettingsViewModel` wires flows only; the shaping lives in the pure `toSettingsUiState`/label functions in `SettingsMapper`. **`SettingsUiState.sample()` is `@Preview`-only** — production builds the state directly from real defaults (it used to be `sample().copy(...)`, which shipped mockup copy as the source of truth).
  - **Arity:** both `combine` calls in `SettingsViewModel` are at the typed five-flow limit. A new setting goes into the private `SettingsValues` holder or a sibling holder — never as a sixth top-level argument.
  - **Theme is special:** it lives in `UnPawseApp` so it can drive the whole app. `ThemeMode` (`ui/theme/ThemeMode.kt`) is the tri-state the user picks; the persisted form is still a nullable `Boolean` where absent means "follow system", and `setDarkModeOverride(null)` is what clears it. A two-position `Switch` could only ever write `true`/`false`, so the follow-system state was unreachable once touched.
  - **Settings that other components read** are exposed as `StateFlow`s on `AppContainer` — `catDetectorMinConfidence`, `earnedMinutesPerCat`, `warningMinutes`, `reminderMinutes` — and consumed as `() -> T` lambdas. That keeps DataStore out of `UsageTracker`/`CatDetector`/`CameraViewModel` and means a change takes effect on the next tick or capture without rebuilding anything.
    - **These four must NOT be `by lazy`** — every other container property is, so this is the one deliberate exception and it is load-bearing. `stateIn` seeds the flow with the *default* and swaps in the persisted value only once DataStore's first emission lands. Each of these is consumed by a lambda whose **first invocation is the decision itself**, so with `by lazy` the flow is created at that instant and `.value`, read microseconds later in the same expression, is always the default. Reproduced on-device: the camera granted 15 minutes instead of the user's configured 10 (and 20), and judged the first photo of every process against the 0.7 default gate instead of their sensitivity setting — logged `gate=0.7` on the first capture, `gate=0.5` on the second. Initialising eagerly starts collection in `Application.onCreate`, well ahead of any UI, including the cold launch-into-camera path from the block overlay. A new settings mirror added here must follow suit.
  - **The container also owns `DailySummaryWorker` scheduling**, collecting `dailySummaryEnabled` and scheduling/cancelling. Doing it there rather than in the ViewModel keeps the schedule correct for a process that never opens Settings.
- **Camera / detection.** `CameraViewModel` runs the pipeline *take photo → classify → save-if-cat*; the CameraX controller stays lifecycle-bound in the composable (`CameraRoute` passes a suspend capture lambda in). `CameraEvent` (`Saved` / `NotACat` / `Error`) is a one-shot `Channel`; `CameraRoute` acts on exactly one thing — dismissing the block overlay when a capture actually earned time (see the reward loop below) — because everything else already surfaces through the hint text. `CatDetector` wraps all ML behind one class; `classify` is a pure gate. Captures persist as app-internal JPEGs via `PhotoStorage` (no media permission).
- **Foreground detection & enforcement (`service/`).** `ForegroundAppMonitor` is the interface; `UsageStatsForegroundAppMonitor` polls `UsageStatsManager.queryEvents` every ~1s, querying only events *since the last tick* and **folding them into a stack of what is on screen** (so sitting still in one app keeps reporting it). It has three answers, not two: an app, or `null` for *unknown* — the screen is off, nothing has been seen yet, or everything it knew about has stopped. Without the screen-off `null` the last app would accrue time all night; without the stack the block was permanently escapable via Recents (see the note under **Resolved**). `UsageTracker` credits the interval *between* ticks to whichever app was in front, gated on `isMonitoredAndEnabled` so unmonitored apps never get a `daily_usage` row, and clamps each tick (`accrualMillis`, max 5s) so a doze/suspend gap can't silently burn a whole budget. It emits `limitReached` **once per breach** (not per tick), re-arming when the user switches away or earns time back. `UsageMonitorService` is a `specialUse` foreground service (required: tracking must survive backgrounding — exactly when the watched app is in front) started via `UsageMonitorController.startIfPermitted`. `UsageAccess` wraps the `PACKAGE_USAGE_STATS` app-op: **no runtime dialog exists**, so the Settings row deep-links to system Settings and the state is re-read on resume (`LifecycleResumeEffect` in the Settings destination, for the permission chips only).

- **Achievements are derived, never stored** (`ui/stats/Achievements.kt`). Each rule answers "what is the earliest date this was first true?" by re-reading the history, so there is no achievements table, nothing to migrate, and no way for a stored flag to drift from the data behind it — delete a run of photos and the streak badge correctly goes away again. The date is what makes "Recent Achievements" sort by genuine recency rather than catalogue order. All pure and parameterised on `today`, like every other mapper.
  - **The mockup's own three badges are not implemented, deliberately.** "Deep Focus / 4h Without App Swap" and "Night Owl / No Phone After 10PM" aren't derivable from anything stored — `daily_usage` holds per-app *daily totals* with no session or app-swap history, and `FocusSession` keeps only a live end time. Inventing them was the alternative, which is the thing this screen exists not to do. The five shipped rules (First Cat, 7-Day Streak, Cat Collector, Under Budget, Well Blocked) are each backed by data that actually exists.
  - **Two guards in "Under Budget" carry its whole meaning**: *today never qualifies* (it is still in progress — a badge awarded at 9am and revoked by lunchtime is worse than one awarded a day late), and the day must have *some* usage (without that, every day the phone sat in a drawer would earn it and the badge would mean nothing).
  - **Locked badges are rendered, not hidden** — the mockup's greyed "Coming Soon" card. This reverses the earlier "hide the empty section" rule for a good reason: the catalogue is fixed, so a fresh install showing five locked cards is *content* (it says what there is to earn), whereas the old empty section under a heading read as content that failed to load. Only the `opacity-50` half of the mockup's `opacity-50 grayscale` is reproduced: true desaturation needs a saturation `ColorMatrix` via `RenderEffect`, API 31+ against minSdk 26. That is finished, not pending.
  - **`AchievementIcon` is an enum mapped to an `ImageVector` by the screen**, keeping Compose types out of UI state. It replaces an `if (color == CORAL) MilitaryTech else Nightlight` hack that only ever worked because there were exactly two hardcoded badges.
  - **The Stats VM reads the full usage history one-shot, not as a flow.** `UsageTracker` writes `daily_usage` about once a second while a monitored app is in front, so a live full-history flow would re-deliver and re-fold every row on every tick to recompute facts that are by definition historical. Same pattern `AppPickerViewModel` uses for installed apps. Consequence, and an accepted one: a badge earned during a visit shows up on the next one. The per-day series are pre-combined into a private `StatsHistory` holder so the top-level `combine` stays at three arguments — the arity rule `SettingsViewModel` already lives under.
- **Device unlocks (`data/unlocks/`).** `daily_unlocks(date PK, unlockCount)` counts how often the phone was unlocked, behind the Stats "Unlocks" card. Fed by `UnlockReceiver`, **context-registered by `UsageMonitorService`** rather than declared in the manifest: `ACTION_USER_PRESENT` is an implicit broadcast and is not on the Android 8 exemption list, so a manifest receiver would never fire on any level this app supports (visible in `dumpsys activity broadcasts history`, where Chrome's and stk's manifest receivers for it are logged as "skipped by policy at enqueue"). The service is already awake for exactly as long as monitoring is on, so this costs no extra process lifetime.
  - **Register it `RECEIVER_EXPORTED`, and don't "tighten" it to `NOT_EXPORTED`.** The flag gates which *sender* UIDs may reach the receiver, and this broadcast comes from the system, not from us. With `RECEIVER_NOT_EXPORTED` the registration looks completely healthy — it appears in `dumpsys activity broadcasts` under `android.intent.action.USER_PRESENT`, in the delivery list, `#receivers=1` — and `onReceive` is simply never called, with nothing logged anywhere. Exported is not a weakness: `USER_PRESENT` is a protected broadcast, so only the system can send it.
  - **Not `UsageEvents.Event.KEYGUARD_HIDDEN` / `SCREEN_INTERACTIVE`**, which would let the existing ~1s `queryEvents` poll carry this *and* would cover time the service was down — both constants are **API 28** and minSdk is 26.
  - **A daily counter, not an event log**, for the same reasons as `daily_usage`: the date key gives free daily reset, nothing needs individual timestamps, and an unbounded event table would need a purge worker. It is its own table rather than a column on `daily_usage` because unlocks are device-wide — a sentinel package name would leak into the Stats totals, the category breakdown and the export.
  - **The metric is honestly scoped.** Unlocks are only observed while the service runs, so the card reads "TODAY, WHILE MONITORING" and the mapper reports **today's count, not the mockup's "24/day" average** — an average would divide a partial tally by days it wasn't measuring. An empty store reads "—" (the service may never have run); rows present but none today is a real "0".
  - `unlockRepository` is `by lazy` on the container and **must not** join the five eager exceptions: its first read is a UI read or a receiver write, never a blocking decision taken in the same expression that creates it.
- **Blocking schedules ("when", as opposed to a budget's "how much").** A `ScheduleWindow` (`data/schedule/`) is a recurring wall-clock window — start and end as minutes since local midnight, plus a days bitmask — that blocks apps outright, whatever budget is left. `packageName == null` makes it global (every monitored app); otherwise it is scoped to one. The whole rule lives in pure functions in `ScheduleMath.kt`, mirroring `UsageMath.kt`; `ScheduleGate` (`service/`) supplies only the clock, shaped like `FocusSession` and fed by an **eager** `scheduleWindows` mirror on `AppContainer` (same non-lazy reasoning as the settings mirrors — its first read *is* a blocking decision).
  - **A window whose end is at or before its start wraps past midnight, and the days mask then names the day it *starts* on.** "Bedtime 22:00–07:00, Fri" therefore runs Friday 22:00 to Saturday 07:00, which is what someone picking "Friday night" means; the tail after midnight is matched by testing the *previous* day against the mask. `start == end` falls out of the same branch as a full 24 hours, which is the only sensible reading of "from 08:00 until 08:00".
  - **Precedence is FOCUS > SCHEDULE > LIMIT**, decided in `UsageTracker`. It runs from most deliberate to least, and the first two are both escape-less — so when a window and a spent budget coincide the user gets the schedule overlay with **no camera button**. Offering it would be a promise the app can't keep: earned minutes raise a *budget*, and no amount of budget makes it not be bedtime. `BlockEvent` carries the window's `endsAtMinuteOfDay` so the overlay can say what the block is until without re-reading the schedule.
  - **`UsageTracker.blockReleased` is how the overlay comes down without an app switch.** A focus session has an end time the service can `delay` on; a window just stops covering the current minute. Rather than add an alarm, the tracker — already evaluating every tick — emits the package when *every* block reason has cleared, and the service hides the overlay if it matches. Not schedule-specific: it also lifts a limit block the moment earned time puts the app back in budget. Boundaries are therefore **best-effort within one poll interval** while the service is alive; nothing wakes the device at a window's edge.
- **Weekday/weekend budgets.** `monitored_apps.weekendLimitMinutes` is a nullable override: `null` follows `dailyLimitMinutes`, a positive value is a separate Saturday/Sunday budget, and `UNLIMITED_MINUTES` means no cap (so "weekday-only limits" is expressible). **The sentinel is negative, not zero** — a limit of 0 already means "over budget from the first second" throughout the enforcement path and several tracker tests rely on it, so overloading zero would have flipped them from "blocked instantly" to "never blocked". `effectiveLimitMinutes` resolves the split against the same `today()` the usage row is keyed by. `remainingMinutes` returns **null on an uncapped day**, which the warning path already treats as "nothing to warn about"; `UsageRepository.setLimit` carries an existing override across so the monitor switch and the limit stepper can't silently reset it.
- **`daily_usage.blockedCount` records blocks raised**, one per breach, and is what Stats' "Prevented" card reports. Written from **`UsageTracker`, on the line after `_blockRequired.emit`** — not from `UsageMonitorService.observeBlockRequired`, which is where the overlay actually goes up. The tracker branch already owns the once-per-breach `signalledFor` de-dup and already holds the repository, so the stored count is provably the same set of events as the flow; putting it in the service would add a `SharedFlow` hop and move it into Context-bound, device-verified-only territory. The service is the only consumer and never filters an event out, so the two sites are semantically equivalent.
  - **A block row rather than a `block_events` table**: a block is a per-app, per-day fact keyed exactly like usage, so the composite key already gives it free daily reset and the `@Transaction` insert-then-increment already gives it atomicity — and Stats' existing `observeRecentUsage(14)` already loads it, so no new flow and no pressure on the combine arity. An event table would buy time-of-day analysis nothing asks for, at the cost of unbounded growth plus a `CaptureRetentionWorker`-style purge.
  - **Counting semantics:** `signalledFor` re-arms on an app switch, so leaving a blocked app and returning counts as a **second** prevented interruption. That is deliberate — it is a second time the user was stopped — so don't "fix" it into once-per-day. All three reasons count: a focus session and a schedule window prevent an interruption just as a spent budget does.
- **`monitored_apps.category` is carried across by the same rule.** The column is a nullable `AppCategory.name` — nullable so "nobody has classified this" stays distinguishable from a deliberate choice of `OTHER`, though both render as Other. `setLimit`'s `defaultCategory` parameter only ever **seeds a row that doesn't exist yet** (the platform's guess at first enable) and never overwrites a stored value, because the picker passes it on every stepper nudge too; without that rule a limit change would silently undo the user's category choice. `MonitoredApp.category` is non-null — the null is resolved in `toDomain()` so no consumer handles it.
- **Starting the monitor is `startIfPermitted`'s job alone, called from several triggers — never inline a start elsewhere.** It is the single gate and is idempotent + self-refusing: it no-ops without usage access, and it **catches `ForegroundServiceStartNotAllowedException`** (an `IllegalStateException`, so no `SDK_INT` branch) and returns `false` rather than crashing when the platform forbids a background FGS start (API 31+). Triggers, in order of coverage: (1) an app-wide `LifecycleResumeEffect(Unit)` in `UnPawseApp` — fires on **every** resume regardless of tab, so returning from the usage-access screen to *any* screen starts it (the original bug was that only the Settings tab did); (2) `UnPawseApplication.onCreate()` — covers cold starts that never resume the UI (launch-into-camera from the block, a `START_STICKY` revival); (3) `BootReceiver` on `BOOT_COMPLETED` — covers reboots; (4) `MonitorHealthWorker`, a 15-minute periodic `WorkManager` job scheduled from `onCreate` (`KEEP` policy, so it neither duplicates nor resets) — the self-heal for when `START_STICKY` and the receiver are both defeated by an OEM battery manager, so monitoring recovers within a period instead of staying dark. All four route through the one gate and add no logic of their own; a killed/rate-limited trigger self-heals on the next one.
  - **Why the catch is not defensive paranoia:** on a real reboot, `Application.onCreate()` runs *before* the broadcast reaches the receiver, in `uidState: CEM` with no boot allowlist, so its start genuinely throws — verified on an API-36 emulator, where the catch swallowed it 10 ms before `BootReceiver` (now in `uidState: RCVR`, holding the 20 s `reasonCode:BOOT_COMPLETED` temp-allowlist) started the service into the foreground. Without the catch the app would crash in `onCreate` on **every** boot.
- **The block overlay (`BlockOverlayHost`/`BlockOverlayController`).** When `limitReached` fires, the service draws `BlockOverlayScreen` in a `TYPE_APPLICATION_OVERLAY` window over the offending app (needs `SYSTEM_ALERT_WINDOW`, which also grants the background activity launch used by "Open Camera"). The window is intentionally **touchable and focusable** — it must swallow input to the app underneath. Compose normally inherits its lifecycle/saved-state/ViewModel/back-dispatcher owners from an Activity; there is none here, so `BlockOverlayHost` *is* all **four**. Hosts are **single-use** (a `LifecycleRegistry` can't return from `DESTROYED`), so the controller builds a fresh one per show. All of it is **main-thread only** (`WindowManager.addView`), hence the `withContext(Dispatchers.Main)` in the service.
  - **Back is swallowed**, via `BlockOverlayScreen(interceptBack = true)` and a `BackHandler` that does nothing. **Verified on an API-36 emulator:** with Chrome over its limit the overlay came up, four back presses left it untouched (and never reached Chrome underneath), while "Exit App" still dismissed and went home.
    - **The view-tree owners must be set on the window's root view**, which is now `BackSwallowingContainer`, not the `ComposeView` inside it. Compose resolves its recomposer from the window root, so setting them a level down throws `IllegalStateException: ViewTreeLifecycleOwner not found` the instant the overlay attaches — it crashed exactly that way first time, and no unit test can catch it because the whole thing is `WindowManager`-bound.
  - Making back actually fire took three more things, and all three are load-bearing: (1) the host owns an `OnBackPressedDispatcher` and calls `setViewTreeOnBackPressedDispatcherOwner`, or the `BackHandler` throws on the first block; (2) on **API 33+** the press arrives via `OnBackInvokedDispatcher`, wired with `findOnBackInvokedDispatcher()` **after** `addView` — the dispatcher hangs off the `ViewRootImpl`, so an unattached view has none; (3) on **API 26–32** nothing calls `onBackPressed()` (normally the Activity's job), so a `BackSwallowingContainer : FrameLayout` wraps the `ComposeView` and overrides `dispatchKeyEvent`. It is a wrapper because `ComposeView` is final, and `dispatchKeyEvent` rather than an `OnKeyListener` because a `ViewGroup` hands the event straight to its focused child — a listener on the parent never fires, which is how a naive version silently does nothing. It also consumes `ACTION_DOWN`, or the app underneath sees half a press.
  - `interceptBack` defaults to **false** and only the overlay window sets it. The in-app debug route (`UnPawseNavHost`) and the `@Preview` have no dispatcher owner, and `BackHandler` null-checks `LocalOnBackPressedDispatcherOwner` *regardless of its `enabled` flag* — hence the `if (interceptBack)` guard rather than `BackHandler(enabled = …)`. Swallowing back on that route would also trap the user there.
  - This hardens **back only**. Home and recents are delivered to the system, never to an application window; intercepting them needs the `AccessibilityService` this project rejected, so the escape remains by design.
  - **Gotcha:** anything rendered in this window runs *outside an Activity*. `UnPawseTheme` therefore casts with `view.context as? Activity` — an unconditional cast crashed the app with `ClassCastException: UnPawseApplication cannot be cast to Activity` the first time the block fired. Keep Activity assumptions out of composables that the overlay can reach.
  - Both overlay buttons must dismiss first: the overlay sits above *every* app including our own, so leaving it up would cover the camera. "Exit App" goes home rather than back into the blocked app; returning re-triggers the block anyway, so the limit holds.
  - An overlay window **outlives app switches by design**, so the service also hides it whenever the foreground moves off the blocked app (`dismissBlockWhenUserLeaves`). Without that, a home gesture strands the block on top of the launcher. The tracker republishes the foreground app as a `StateFlow` for this — don't collect `ForegroundAppMonitor.foregroundApp()` again, it's a cold flow and would start a second poller.
- **The reward loop.** `BlockSession` is the thread between the block and the camera: the service arms it with an `ArmedBlock` (id + package + `armedAtMillis`) when raising the overlay, and `CameraViewModel.creditBlockedApp` settles it when ML Kit confirms a cat. **No explicit "unblock" step exists**: crediting lifts the budget above what's been used, so `isLimitReached` goes false and the tracker simply stops signalling. The session deliberately outlives the overlay (the debt survives "Open Camera" taking the block down) but is cleared by "Exit App". `CameraEvent.Saved` carries a `RewardOutcome` so the hint can say what the cat was worth; crediting is ViewModel work, while `CameraRoute` takes down the overlay (a window this side owns) **only on `RewardOutcome.Earned`** — leaving it up after a refusal, since the app is still blocked.
  - **The escape hatch is bounded, and the bounds are the point.** It used to have no floor: a block re-arms the moment the granted minutes are spent, so photo → 15 min → photo → 15 min repeated forever and a static cat photo on a second screen defeated the daily limit entirely. Three independent bounds now apply, each with its own reason for living where it does:
    1. **A 5-minute redemption window** (`BLOCK_REDEEM_WINDOW_MINUTES`). `BlockSession.current()` returns the armed block only inside it and clears a lapsed one on read — lazy and self-healing, because nothing needs to *react* to a window closing and a coroutine per block would be state to leak. This closes the back door left by `dismissBlockWhenUserLeaves`, which hides the overlay without clearing the debt: without a window, a session armed this morning was still redeemable tonight by a casual capture from the Camera *tab*. **Not persisted, unlike `FocusSession`** — five minutes spanning a process death isn't worth a DataStore key plus a container collector, since the overlay is gone too and returning to the app re-arms within a tracker tick.
    2. **A per-app daily cap** (`DAILY_EARNED_CAP_MINUTES`, 60 — four cats at the shipped grant). Needed **no schema change**: `earnedSeconds` is only ever incremented, so today's value *is* today's cumulative grant total, and `(packageName, date)` already resets it at midnight. A grant is trimmed to whatever is left of the cap rather than refused outright, so `earnedSeconds` never passes it and the last cat of the day still buys something.
    3. **A per-app cooldown** (`REWARD_COOLDOWN_MINUTES`, 10), stamped into `daily_usage.lastEarnedAtMillis` by the same `@Transaction` that increments `earnedSeconds`. **Persisted precisely because the session isn't**: it is the defence against the fast loop, so it must not be resettable by force-stopping the app. A backstop rather than the primary bound — at the 15-minute grant it never bites; it bites at small grant settings, where a 5-minute reward could otherwise be re-earned every 5 minutes.
  - **`UsageRepository.tryEarnMinutes` is the only sanctioned credit path** — it applies all of the above and returns a `RewardDecision`. `addEarnedMinutes` remains the uncapped primitive for seeding and tests; calling it from the reward loop bypasses the cap silently. The decision logic is pure and top-level in `data/usage/RewardPolicy.kt`, beside `UsageMath.kt` and for the same reason. **The cap is reported ahead of the cooldown** when both apply: waiting out a cooldown that ends in a refusal is worse advice than "you're done for today".
  - **A refusal the user can't explain reads as the app being broken**, so each outcome says something different. `RewardOutcome` (`NoActiveBlock` / `Earned` / `DailyCapReached` / `CoolingDown`) drives `savedHint` in `ui/camera/CameraHints.kt` — pure top-level functions, like `warningText`, so the copy is unit-tested. And when an app has spent its allowance the overlay uses `BlockUiState.forAppOutOfRewards` (`showCamera = false`, reusing the affordance built for focus mode) and the service **does not arm a session at all**: offering an escape that would refuse the photo is worse than offering none.
  - **A capture records what it was worth** (`CaptureEntity.earnedMinutes`, 0 when it bought nothing), written by a follow-up `recordEarnedMinutes` after the credit rather than as a `saveCapture` parameter — the photo is stored *before* the credit is attempted, so a crediting failure can't cost the user their photo, and a row that never gets updated reads as "earned nothing", which is true. It has to be stored because nothing can reconstruct it: `daily_usage` holds a running per-app total with no link back to the photo. Home's Recent Activity previously asserted `"Time earned back."` for **every** cat, so spamming the shutter on a fresh day looked like it was working; it now reports `earnedMinutes` or says only that the photo was saved. Same rule as the Stats note above — don't state a number the app didn't compute.
  - Verified cats are **still saved when they earn nothing** (and still count toward the Home "Cats" pill and the streak): unPawse is a cat-photo app, the gallery and the streak are about photographing a cat daily, and neither claims anything about rewards. The bounds limit what a photo can *buy*, not whether it can be taken.
  - **`isBonus` is a *streak* fact, orthogonal to the reward.** It is set at insert time by `isStreakMilestone` (`data/capture/Streaks.kt`) when the capture is the day's **first** and lands a streak of `STREAK_CELEBRATION_DAYS` (3) or more — the same threshold the Home banner celebrates, and every day past it still counts. A capture can be a bonus, an unblock, both, or neither; crediting the blocked app is decided separately and neither branch reads the other. The Gallery marks a bonus with the blush card, an "Bonus" label and "Daily streak bonus!". It **does keep its AI badge** — a milestone capture cleared the detector like any other, and blanking the confidence hid a number the app really computed.
    - The rule must read the capture history **before** the insert. Afterwards today is already a capture day and it can only answer false; `CaptureBonusTest` pins that as a regression. `saveCapture` stamps `capturedAt` from the wall clock while the caller passes an injected `today`, so a test exercising both has to pin them together.
- **App picker + package visibility.** `InstalledAppsProvider` (`data/apps/`) fences off `PackageManager` so ViewModels stay testable. It queries **only LAUNCHER-resolvable apps**, which is the deliberate, restrained answer to Android 11+ package visibility: it needs the `<queries>` intent element in the manifest but **not** `QUERY_ALL_PACKAGES` (which triggers Play Store sensitive-permission review). Consequence: non-launchable apps never appear in the picker — fine, since you can't spend screen time in an app you can't open.
  - **App categories** (`data/usage/AppCategory.kt`: SOCIAL / PRODUCTIVITY / ENTERTAINMENT / OTHER) come from `ApplicationInfo.category`, read off the `ResolveInfo` the picker query **already returns** — no second `PackageManager` call, no extra flags, and **no new permission**, since it's only ever read for apps that are launchable and therefore already visible to us. `categoryFromPlatform` is pure and top-level so the whole map is tested without a device.
  - **The map is deliberately conservative.** Only `CATEGORY_SOCIAL`, `CATEGORY_PRODUCTIVITY` and the four media categories (`GAME`/`AUDIO`/`VIDEO`/`IMAGE`) map. `CATEGORY_NEWS` and `CATEGORY_MAPS` map to `null`, as does anything from a newer platform. The field is declared by each app's *own* developer and is frequently absent, so forcing a news reader into "Entertainment" would be unPawse asserting something it doesn't know — the same failure the Stats blanking rule exists to prevent. Everything unmapped shows as **Other**, which is a real bucket rather than a hole, and the user corrects it in one tap. App **icons are loaded lazily per visible row** (`ui/apppicker/AppIcon.kt`, `produceState` + IO) rather than eagerly for every app, keeping `Drawable`s out of UI state and off the main thread.
- **Navigation:** single-activity, `navigation-compose` with **plain string routes** (`Routes`), deliberately **not** kotlinx-serialization type-safe routes (avoids a second compiler-plugin/version-matching dependency). Tabs use `popUpTo(start){saveState}; launchSingleTop; restoreState`. Settings rows emit ids (`SettingsRowIds`); `SettingsRoute` — not the NavHost — maps them to a destination or a system intent, so the navigation graph knows nothing about Settings' internals. **Every declared id now leads somewhere**; the `when` has an explicit `else` so a future unhandled id is a visible gap rather than a silent fall-through. The **Block Overlay** is a normal destination (no bottom bar) temporarily reachable from Home's "Pause Protection" card — this stays as a debug/preview entry; the real limit-reached trigger is being built (see Open Decisions + roadmap).
- **Theme:** `UnPawseTheme(darkTheme, content)` maps all `DESIGN.md` tokens to a `lightColorScheme`; no dynamic color (blush-pink brand identity is intentional). The **dark scheme is provisional** (derived from fixed/inverse tokens) — refine against a real dark mockup.
- **Typography:** the type scale matches `DESIGN.md`, but the family is currently the **platform sans-serif**, not Inter. To switch to Inter: drop the four OFL TTFs into `res/font/` and replace `AppFontFamily` in `ui/theme/Type.kt`.
- **Icons:** `material-icons-extended` — the ~40 mockup symbols map nearly 1:1; R8 strips the unused ones. Notable substitutes: `Shield` (Pause Protection), `GridView` (Gallery), `LocalCafe`, `PhoneAndroid`.
- **Insets:** `enableEdgeToEdge()`; `Scaffold` inner padding is applied as lazy-list `contentPadding` so content scrolls under the bars; Camera consumes only the status-bar inset; Block uses `safeDrawingPadding()`.
- Add new dependencies via the version catalog and reference them as `libs.*`. Package everything under `com.example.unpawse`.

  - **Verified end-to-end on an API-36 emulator.** Toggling Chrome on showed **Productivity** straight away, which is the load-bearing check: `ApplicationInfo.category` really is populated on the `ResolveInfo` the picker query already returns, so no second `PackageManager` call is needed. Overriding it to Social stuck, and **nudging the daily-limit stepper 30m → 45m left it on Social** rather than reverting to the platform's guess — the `setLimit` carry-across regression. Calendar seeded as Productivity from the platform. With real foreground time in both, the donut drew two arcs whose sizes tracked the actual seconds (Calendar roughly twice Chrome), legend labelled by **category** rather than app name, and the empty Entertainment/Other buckets were absent.
  - Wrinkle, pre-existing rather than introduced: a bucket under 60 seconds draws a real arc but its legend reads "0m", because `formatSeconds` floors. Same rounding the daily total has always used, and unreachable at everyday usage levels, but it is the one place a proportion and its label can look like they disagree.
- **Stats' "Prevented" card is real** (DB **v8**, export **v4**). `daily_usage.blockedCount` counts every block raised; the card reports the Mon–Sun total and says "THIS WEEK". **Verified on an API-36 emulator:** with Chrome monitored and a 15-minute focus session running, opening Chrome raised the escape-less overlay and opening it a second time raised it again — Stats then read **2**, not 16, despite each overlay standing for ~8 seconds (8+ tracker ticks), which is the de-dup holding. The count survived a reinstall. The export field is covered by `ExportSnapshotTest` rather than a SAF walk.
- **Stats' "Unlocks" card is real** (DB **v9**, export **v5**). **Verified on an API-36 emulator**, which needed `adb shell locksettings set-disabled false` first — the stock AVD ships with **no keyguard**, so `ACTION_USER_PRESENT` is never broadcast at all and the card sits at "—" no matter what you do. `adb shell am broadcast -a android.intent.action.USER_PRESENT` is not an alternative: it is a protected broadcast the shell cannot send. With a keyguard enabled, sleep → wake → swipe raised exactly one broadcast and one recorded unlock per unlock (`#receivers=1`, no double-counting), and the card read **3** after three of them. Force-stopping the app and unlocking twice more left it at **3**, which is precisely what the "WHILE MONITORING" caption claims.
- **Achievements are implemented** — five derived badges, no schema change. **Verified on an API-36 emulator:** a fresh install showed all five greyed "Coming Soon" cards under the heading, with the rail scrolling horizontally to reach every one. Opening Chrome 26 times against a running focus session drove `Prevented` to exactly **26** (one per open, no drift) and flipped **Well Blocked** to earned — it moved to the front of the rail at full opacity with its real subtitle "25 limits respected", while the rest stayed greyed with a lock. "First Cat" could not be earned on the emulator: the virtual scene has no cat in view, so the shutter honestly reported "Hmm, that's not a cat — try again", which is the camera pipeline working correctly rather than a gap in the rule (which is unit-tested).
- **The Recents escape is closed** (no schema change). **Verified on an API-36 emulator** with Chrome seeded to 1s below its 30m limit, polling the window list and the top activity about once a second:

  ```
  19:54:11  overlay=up    top=chrome     ← opened from the launcher: block fires
  19:54:24  overlay=down  top=launcher   ← swipe to Recents
  19:54:33  overlay=up    top=chrome     ← tap the Chrome card: re-blocks in ~1s
  19:54:57  overlay=down  top=launcher   ← Home
  19:55:06  overlay=up    top=chrome     ← reopen: re-blocks (the path that always worked)
  ```

  So **2/2 by either route**, where Recents was 0/2 before, and `blockedCount` read exactly **3** — one per genuine re-entry, no drift. The silent half is fixed too: sitting in YouTube (monitored, under budget) moved `usedSeconds` **1717 → 1757 across 40 seconds**, a clean 1s per second, with `blockedCount` still 0 — so the counter no longer freezes and stray unknown ticks aren't inventing "Prevented" events.
- **Home and Stats render real data.** Home: today's used/remaining across monitored apps, progress ring, capture streak, today's cat count, active-app count, and an activity feed (currently-blocked apps + today's verified cats). Stats: daily total, vs-yesterday delta, Mon–Sun hours chart, week-over-week trend, budget-left donut, category breakdown, longest streak, lifetime captures. Verified on an emulator against real data (26m Chrome usage, 2 captures): Home and Stats agree, the week chart spikes only on today, and an empty history reads "No data for yesterday" instead of dividing by zero.
- **`SampleData` is down to one entry** — the Block Overlay's in-app debug route. Every `.sample()` elsewhere is `@Preview`-only, and **no mapper builds production state from one any more**: `StatsMapper` was the last holdout and now constructs `StatsUiState` field by field.
  - A related leak survived longer: `ScreenHeader` defaulted `avatarInitial` to **`'S'`** — the mockup's "Sophia" — so Stats and Gallery, which never passed one, showed that letter to every user regardless of their name. The default is gone (the parameter is now required, so a forgetful caller fails to compile), and `ui/format/DisplayName.kt` holds the single `displayNameOf`/`avatarInitialFor` pair that Home, Settings, Stats and Gallery all derive from — Home and Settings previously each had their own copy of the `ifBlank { "friend" }.first().uppercaseChar()` rule. `GalleryViewModel`/`StatsViewModel` take `userName` as a `Flow`, so the avatar tracks a rename live. **Verified on an API-36 emulator:** renaming from "BlockTest" to "Sophia" flipped all three headers B → S without a restart.
- **Known gaps:** **nothing wakes the device at a schedule boundary** — a window takes effect within ~1s of the user being in a covered app, but there is no alarm and no "bedtime starts in 5 minutes" heads-up; there is **no duplicate/liveness check on the photo itself** — the bounds above limit *how much* re-shooting a static cat picture can earn, but re-shooting one still works within them; **home and recents still leave the block** (back is swallowed; the user is simply re-blocked on return — via *either* route since the monitor started tracking a stack, where Recents used to escape permanently); **the unlock count only covers time the monitor service was running**, which the card states on its face rather than implying a complete tally; **a badge earned during a Stats visit only appears on the next one** (the full history is read once per entry, not observed); the mockup's "Deep Focus"/"Night Owl" badges are not implemented because no session or app-swap history is stored; Home's next-break countdown is placeholder copy (no break feature exists — the Settings row that claimed one is now the reward-grant control); an app the platform never classified sits in the Stats donut's **Other** bucket until the user assigns it; **an import shows no progress and cannot be cancelled** — it is fast enough for a realistic library, but a very large one would sit on a toast-less pause.
- **Backup is still the AGP template.** `AndroidManifest.xml` sets `allowBackup="true"` while `backup_rules.xml` and `data_extraction_rules.xml` are untouched samples with the generated `TODO`. Android Auto Backup therefore includes the whole sandbox — the Room DB **and** the cat JPEGs — in the user's cloud backup and in a device transfer. The privacy policy says so honestly rather than claiming everything stays on-device; excluding `files/captures` would make the stronger claim true, but changes restore behaviour, so it is a deliberate open decision rather than an oversight.
- **Permissions the app now needs at runtime:** `CAMERA` and `POST_NOTIFICATIONS` (runtime dialogs), plus two **special** permissions granted only in system Settings — usage access (`PACKAGE_USAGE_STATS`) and "display over other apps" (`SYSTEM_ALERT_WINDOW`). Three of the four have a Settings row — **`CAMERA` deliberately does not**, because it is only ever needed from inside the camera screen, which asks for it there. The two special ones deep-link out and re-check on resume. `POST_NOTIFICATIONS` is asked for by the "Notification access" row and falls back to system notification settings below API 33, or once the system stops showing the dialog. **`CAMERA` has the same fallback**: `RequestPermission` stops showing a dialog after two denials and answers `false` synchronously, so `CameraPermissionState.request` routes to `CameraAccess.settingsIntent` (the app-info page) once `canAskSystemForCamera(askedOnce, shouldShowRationale)` goes false, the prompt's button becomes "Open settings", and `CameraRoute` re-checks on resume. The on-entry auto-request is gated on the same flag — without that gate, merely opening the camera after a permanent denial would fling the user into system Settings. This matters most from the block overlay, whose "Open Camera" deep-links into that screen: before the fallback, a permanently-denied camera left the user with no way to buy their app back. **Verified on an API-36 emulator**, where note that a **single** "Don't allow" is enough to make the denial permanent — the "two denials" rule is pre-API-30 lore, and the inference holds either way because it reads `shouldShowRequestPermissionRationale` rather than counting. The prompt flipped to "Open settings", which landed on unPawse's App info page; granting there and pressing back brought the viewfinder up **without re-entering the screen**, which is the resume recheck. `Notifications.canPost` checks **both** the permission and `areNotificationsEnabled()`, so notifications switched off wholesale don't read as "Granted". `RECEIVE_BOOT_COMPLETED` is a normal install-time permission (no user action). For emulator testing: `adb shell appops set com.example.unpawse GET_USAGE_STATS allow` and `... SYSTEM_ALERT_WINDOW allow`; a freshly-installed app is in the *stopped* state and won't receive `BOOT_COMPLETED` until launched once, so launch it before testing the reboot path.

### Resolved
- **Achievements: a derived rules catalogue, no table.** Resolved with the user: rules evaluate the stored history and return an earned-on date, rather than persisting unlock rows. No schema change, no migration, and the result self-corrects when the data behind it changes.
  - **The mockup's literal badges were rejected** as needing per-session and app-swap history tables built solely to serve them, on top of everything else in the plan.
  - **"First completed focus session" was cut** from the shipped five for the same reason: `FocusSession` stores only a live end time, so awarding it would have meant a new store — contradicting the derived-only decision. Left as a real option if focus history is ever wanted for its own sake.
- **App categories: a column on `monitored_apps`, not a separate table.** Resolved with the user: auto-guess from `ApplicationInfo.category` with a user override in the App Picker, rather than platform-only (a large unfixable "Other" slice, since the field is developer-declared and often absent) or user-only (the donut stays one grey blob until they do the work). Stored as a nullable `String` holding an `AppCategory.name` — no `TypeConverter`, survives a reorder of the enum, and reads correctly in the `sqlite3` dumps the emulator checks use.
  - **Known trade-off:** `daily_usage` rows outlive `removeMonitoredApp`, so an orphaned row has neither a label nor a category. It doesn't bite today — the breakdown filters to enabled apps and to *today* — but a future usage-history view would show those hours as Other. A separate `app_categories` table surviving removal would fix that, at the cost of a table, a join and a purge-lifecycle question, for a screen that doesn't exist.
- **Scheduled blocking and day-varying budgets.** Resolved with the user before implementation:
  - **Both global and per-app windows**, so "bedtime" is set once rather than repeated per app, without giving up finer control.
  - **Weekday/weekend split, not full Mon–Sun.** One nullable override covers the case people actually have ("30m on school nights, no cap Saturday"); seven independent values would have meant a much busier row for a case nobody asked for.
  - **A scheduled block is escape-less**, like focus. Earned minutes raise a budget, so they logically cannot unlock a rule about *when* — the overlay hides the camera button rather than offering an escape it would then refuse.
  - **Best-effort boundaries on the existing ~1s tracker tick**, no `AlarmManager`. An exact alarm plus a heads-up warning was considered and deferred: it adds OEM-doze caveats and a second scheduling mechanism, and the tick already blocks within a second of the user actually being in a covered app. Recorded as a known gap.
- **Settings build-out (all rows).** Resolved with the user, one function per phase:
  - **Daily limit** → a read-only *derived* total of the enabled per-app limits ("4h 15m across 5 apps"), retitled "Total daily limit". unPawse enforces per-app limits only; a global cap would have meant new enforcement in `UsageTracker`, and the old title read as one.
  - **Break duration** → repurposed as **"Time earned per cat"**, the control for `BONUS_MINUTES_PER_CAT`. No break feature exists anywhere in the app, so the row described nothing; the reward grant was a real number that happened to be hardwired.
  - **Confidence threshold** and **Require live photo** → **removed**. The first contradicted the sensitivity slider directly above it (the slider *is* what sets the gate); the second persisted to DataStore with no consumer and nothing to gate, since there is no photo-import path.
  - **Delete history** → a **full reset** (usage, limits, photos, preferences, plus the in-memory focus/block sessions), retitled "Delete all data" and gated behind a dialog that enumerates the loss. The monitor service is deliberately *not* stopped: with no monitored apps it accrues and blocks nothing, and a stop/restart would add a platform-refusable FGS start for no gain.
  - **Export** → a **ZIP bundle** (`export.json` + `photos/`) via the system file picker (SAF `CreateDocument`), so no storage permission is involved. The manifest still carries **no file paths** — a path would leak the private-storage layout into a file the user may share — but from **v6** each capture names its JPEG by bare file name and the bytes ride alongside in `photos/`, which is what makes a restore able to bring the Gallery back. `ExportSnapshotTest` pins the no-paths guarantee by asserting no capture field contains a separator.
  - **Import** → `Settings → Import data`, SAF `OpenDocument`. **Replaces everything**: it reuses `ResetRepository.eraseEverything()` wholesale so the wipe ordering stays defined in one place, then writes the snapshot. The confirm dialog fires *before* the picker, so the warning is read while backing out is still free.
    - **Parse before wipe, always.** A wipe followed by a failed parse would destroy the user's data on behalf of a corrupt file. `ImportRepositoryTest` pins this for a truncated bundle, a foreign zip, junk bytes and a too-new document; nothing is erased and no orphan JPEG is written in any of them.
    - The bundle is read in **one pass** with `export.json` written first, so the manifest is known before any photo arrives and only one JPEG is in memory at a time. `photoFileNameOf` is the Zip Slip guard — the archive is user-supplied.
    - Content is **sniffed, not trusted**: `looksLikeZip` on the first four bytes decides bundle vs. legacy, because DocumentsProviders routinely report both `.zip` and `.json` as `application/octet-stream`. The picker's mime filter ends in `*/*` for the same reason.
    - **v5 and older documents still import** — they carry no photos, so their captures are skipped (a path-less row would be a permanently broken Gallery tile) and `ImportResult.Restored.skippedCaptures` makes the toast say so.
    - Photos are re-written through `PhotoStorage.save`, which mints a fresh UUID path; a stored path is install-specific, so it has to be re-mapped either way. Capture **ids are preserved** (they're app-generated UUIDs, and favourite/earned references hang off them).
    - Two deliberate lossinesses: an unclassified app imports as an explicit `OTHER` (the repository resolves `null → OTHER` at the entity boundary so no consumer handles the null), and `lastEarnedAtMillis` resets to 0 (policy bookkeeping, absent from the domain model and the export). Neither is a new hole — "Delete all data" already resets the cooldown, and the bound that actually limits earning, `earnedSeconds`, does round-trip. `focusEndMillis` is deliberately **not** restored: a stale end time would resurrect a focus block the user never started.
    - `ImportRepository` takes `openDocument: (Uri) -> InputStream?` rather than a `ContentResolver`, the same lambda-instead-of-Context trick as `ResetRepository.clearSettings` — it is what makes the whole class JVM-testable.
    - **Verified end-to-end on an API-36 emulator.** Export wrote a real `.zip` through the SAF picker whose only entry was `export.json` (no captures yet) at `formatVersion` 6. Importing a hand-built bundle then replaced everything in one pass: the display name, the theme (light → dark, applied app-wide), the Chrome limit 30m → 42m, a restored usage row and unlock count, a schedule, and three captures across three days — Home read **3 Streak / 1 Cats / 34m Remaining** (42 + 2 earned − 10 used), and the Gallery rendered the blush **"Daily streak bonus!"** card for today with its AI badge intact and yesterday's restored favourite heart. The three JPEGs landed under fresh UUID paths, which is the `filePath` re-map doing its job.
  - **Privacy policy** → an in-app screen, not a link. There is no hosted policy, and an app with no `INTERNET` permission cannot fetch one anyway.
  - **Theme** → tri-state System/Light/Dark (see the Settings persistence note).
  - **Notifications** → all three built, behind a real `POST_NOTIFICATIONS` request. The pre-lock warning fires from `UsageTracker`; the recap is a WorkManager job; the reminder is an in-service ticker, chosen because WorkManager's 15-minute floor can't express the shorter intervals and a reminder only makes sense while the user is in a limited app — exactly when the service is already awake.
- **Foreground-app detection: `UsageStatsManager` polling** (not `AccessibilityService`). A foreground Service polls `queryEvents` ~1s. Cost: `PACKAGE_USAGE_STATS` (granted via a Settings redirect, not a runtime dialog), a foreground service + persistent notification, **~1s** block latency, and `SYSTEM_ALERT_WINDOW` to draw the block over the offending app.
  - **Measured on an API-36 emulator:** leaving a blocked Chrome and reopening it put the overlay back up in **~0.4s** (including adb polling overhead). It used to be ~1–2s. The tracker evaluated the block against `previousPackage` — the app the elapsed interval was credited to — so on the tick that first saw a blocked app in front, nothing was evaluated for it; it only became `previousPackage` on the *next* tick. Crediting and enforcement are now keyed separately: the interval still goes to whoever was in front **for** it, but the block is evaluated against whoever is in front **now**. The `signalledFor` re-arm had to move *before* that evaluation, or a stale value from the previous visit suppresses the very re-block this buys. `POLL_INTERVAL` was deliberately left at 1s — halving it doubles `queryEvents` calls all day for at best half the avoidable gap.
  - **The monitor keeps a *stack* of on-screen activities, not "whatever resumed last".** The single-slot version made the block **permanently escapable via Recents**, measured at 0/2 re-blocks vs. 2/2 via Home. Every downstream symptom followed from that one sticky field — usage stopped accruing (the launcher isn't monitored), `signalledFor` never re-armed because `currentPackage` never changed, and no block fired again while the user sat in that app, all with the service alive and its notification still claiming to monitor. Nothing in `UsageTracker` changed to fix it; `null` already flowed correctly end-to-end (it is what screen-off emits).
    - **The measured API-36 event trace is the whole design rationale**, and it is not what you would guess. A full swipe-to-Recents-and-back round trip raises **three events, all about the launcher**:

      ```
      19:54:23  ACTIVITY_RESUMED  launcher    ← into Recents. Chrome is NOT paused.
      19:54:31  ACTIVITY_PAUSED   launcher    ← tapping the Chrome card
      19:54:31  ACTIVITY_STOPPED  launcher    ← …and that is all. Chrome never resumes.
      ```

      Chrome's activity stays RESUMED throughout, because gesture-nav Recents is a launcher-hosted overlay that comes up *on top of* the app rather than replacing it. So the app being returned to is recoverable **only by uncovering it** — there is no event that names it. Any rule built on a single slot is stuck on the launcher for good, whatever it does with pauses.
    - **`resolveForeground` therefore models what the activity manager models** (pure and unit-tested, folding one window at a time): a resume promotes an activity to the top, **a stop removes it wherever it sits**, and whatever was underneath resurfaces. The top of the stack is the foreground app; an empty stack is *unknown*, which stays reachable because it is what re-arms the tracker's block.
    - **`ACTIVITY_PAUSED` is deliberately not consumed at all: pausing is not leaving.** An earlier fix cleared the state on a pause naming the tracked activity, which is exactly wrong here — the only pause in the trace above belongs to the launcher on its way *back into* Chrome. Clearing on it merely swapped a monitor permanently stuck on the launcher for one permanently stuck on `null`. Verified: still 0/2.
    - **Transitions carry `className`, and that is load-bearing.** Two screens of one app produce a resume and a stop for *different* activities of the same package; keying the stack on the package alone would let the outgoing screen's stop pop the incoming one.
    - `ACTIVITY_STOPPED` is **API 29 against minSdk 26 and needs no `SDK_INT` branch**: it is a compile-time constant, so it inlines. API 26–28 never emit it, where this degrades to "whatever resumed last" — i.e. to the behaviour those devices already shipped, not to something worse. The stack is capped (16) so those levels can't leak entries forever. `@Suppress("InlinedApi")` records it.
    - **The cursor is not advanced while the screen is off.** The query is still skipped (battery), but the first waking tick then covers everything that happened in the dark, instead of stepping over it and leaving the stack describing a world that has moved on. The stack itself survives the screen being off, because waking doesn't re-resume anything — the app really is still on top.
  - Two behaviour changes fall out, both improvements: a block now fires before any time is credited for that visit (the user is already over budget), and the current app is evaluated on the service's first tick rather than its second. The second one shifted one warning test — a 1-minute limit now warns at `remaining = 1` on entry rather than `0` after a second's credit. **Why not AccessibilityService:** it would be near-instant, notification-free, and could redirect without an overlay permission — but Play Store review rejects most non-accessibility uses of it, it can read screen content (privacy scrutiny), and the permission ask is far heavier. The latency and notification are an acceptable price for a shippable app. `ForegroundAppMonitor` is an interface, so an Accessibility implementation could be slotted in later without touching callers.
- **Dependency injection:** manual, **app-scoped `AppContainer`** on a custom `Application` (not Hilt/Koin) — preserves the no-extra-compiler-plugins stance.
- **Data/persistence:** **Room** for structured/relational data (captures; per-app limits + usage next) and **Preferences DataStore** for scalar settings. (No remote API.)
- **Camera/detection:** **implemented** — CameraX capture + ML Kit on-device cat verification behind `CatDetector`.
- **UI toolkit:** Jetpack Compose + Material 3 (Views/XML removed).
- **Restart monitoring after reboot: a `BOOT_COMPLETED` `BootReceiver`** that only calls `UsageMonitorController.startIfPermitted` (no start/stop logic of its own). **`BOOT_COMPLETED` only, deliberately not `LOCKED_BOOT_COMPLETED`:** the latter is delivered solely to `android:directBootAware` components, and ours can't be — the Room DB and settings DataStore both live in credential-protected storage, unreadable until first unlock. Nothing is lost by waiting: a locked device can't run the apps we watch, so there's no screen time to track before the unlock that `BOOT_COMPLETED` already follows on FBE devices. The manifest comment records this so it isn't "helpfully" re-added.
