## Overview

**unPawse** is a cat-themed **screen-time manager**: when an app's daily time limit is reached, the user must photograph their cat (verified on-device) to earn more time.

**The core loop works end-to-end**: pick apps and limits → a foreground service tracks real usage → hitting a limit draws a block over the offending app → photographing a verified cat credits bonus minutes and lets you back in → Home/Stats/Gallery render that real data. Every screen is backed by a real ViewModel + repository; `SampleData` survives only for the Block Overlay's in-app debug route. Screens stay stateless `XxxScreen(state, callbacks)`, so state can be re-sourced without touching them. What's left is polish and the gaps listed under **Current State**.

The design system ("Warm Minimalist") centers on a blush-pink (`#F5B6C8`) / plum (`#815060`) Material 3 palette over a warm-white surface, Inter-style typography, 24dp rounded cards, pill buttons, and a "squishy" 98%-press-scale feel. Source tokens live in the mockup's `DESIGN.md`.

## Architecture & Conventions

- **Dependency injection: manual, app-scoped.** `UnPawseApplication` builds a single `AppContainer` (`data/AppContainer.kt`) that owns the Room `CaptureDatabase` singleton, the shared `CaptureRepository`/`PhotoStorage`, the `SettingsRepository`, and derived app-wide state (e.g. `catDetectorMinConfidence`). ViewModel `factory(context)` methods read dependencies from it via `context.appContainer()` — they no longer rebuild the graph each time. `AppContainer` is an interface (`DefaultAppContainer` is the production impl) so tests can supply fakes. This is deliberately **not** Hilt/Koin — it keeps the "no extra compiler plugins" stance; the container is the seam a framework would later replace.
- **Data layer / repositories.** Each store follows the `CaptureRepository` pattern: one class exposes `Flow`s + `suspend` writers so callers never touch Room/DataStore directly. Room stack lives per-feature package: `@Entity` + a separate domain model + an `internal fun …toDomain()` mapper + `@Dao` returning `Flow`. There is **one database** — `CaptureDatabase` (historic name; now app-wide, holding `captures` + `monitored_apps` + `daily_usage`), reached via `getInstance()` and owned by the container. Pre-release schema changes bump `version` and rely on `fallbackToDestructiveMigration`; add real `Migration`s + `exportSchema = true` before shipping.
- **Usage tracking.** `UsageRepository` (`data/usage/`) is the source of truth for *what* is monitored (`monitored_apps`: package, label, `dailyLimitMinutes`, `enabled`) and *how much* has been spent (`daily_usage`, composite key `(packageName, date)` — a new day is a new row, so **daily reset is free**). Usage is stored in **seconds** for precision (the foreground monitor accrues sub-minute ticks) and exposed in minutes. Accrual goes through `@Transaction` DAO helpers that insert-if-absent then `+=`, so it's atomic. Limit arithmetic lives in pure, unit-tested functions (`UsageMath.kt`: `remainingSeconds` / `remainingMinutes` / `isLimitReached`), and reward-policy arithmetic beside it in `RewardPolicy.kt` (`decideReward` / `earnableMinutes`). The repository takes an injectable `today: () -> LocalDate` so rollover is testable and midnight-safe (each call re-reads it), plus a `now: () -> Long` for the reward cooldown.
- **UI state:** every screen is a stateless `XxxScreen(state: XxxUiState, …callbacks)` with an `XxxUiState.sample()` kept **for `@Preview` only**. Each live screen adds a stateful `XxxRoute` that owns a `ViewModel` (built by `XxxViewModel.factory(context)`) and collects `uiState` with `collectAsStateWithLifecycle()`. Every screen now follows this except the Block Overlay, whose state is *pushed in* (the service constructs `BlockUiState.forApp(label)`), so it has no ViewModel. Keep non-trivial mapping in pure, testable top-level functions (`toHomeUiState`, `toStatsUiState`, `toGallerySections`, `toAppLimitItems`, `classify`) — the ViewModel should only wire flows together.
  - ViewModels that mostly reshape one screen's data use `XxxUiState.sample().copy(...)` as a base so the not-yet-real fields keep their mockup copy in one place. **This is only OK for *copy*, never for metrics** — see the Stats note below.
- **Don't ship invented numbers.** `StatsMapper` blanks any metric with no feature behind it rather than inheriting `sample()`'s figures: a fabricated "42 interruptions prevented" sitting beside real ones reads as fact. A test pins this. Restore each only when the feature behind it exists. Still blanked: `unlocks` ("—", no unlock tracking) and `achievements` (empty, no rules engine). **`preventedCount` has graduated** — it is now a real count of blocks raised (see the `blockedCount` note under Usage tracking). Placeholder *copy* (greeting, banner, next-break countdown) is fine and is flagged in the mappers.
  - **A restored metric must also state its period.** The mockup's "Prevented / 42" said nothing about what it counted. It now counts the **Mon–Sun week** and the card says "THIS WEEK" on its face — the same week the chart draws and the trend compares, extending the rule below to a third card.
  - The same trap catches **mockup affordances that were never wired to state**. When a card's icon, colour, direction or *size* encodes a claim, it needs a state field like any other number. Three instances have been found and fixed, all in `StatsScreen`, and they are worth reading as a set because each survived a pass that was looking for fabricated *numbers*:
    1. The **trend arrow** was hardcoded to `TrendingDown` (the mockup's value was "-5.2h"), so a week where usage *rose* rendered "+0.6h" beside a downward arrow. Now driven by `StatsUiState.trendIsUp`.
    2. The **vs-yesterday arrow** was hardcoded to a green `ArrowDownward`, so a day where usage doubled rendered "100% from yesterday" as though it were an improvement. `deltaIsPositive` had existed and been tested the whole time — it was simply never read. Now drives both the arrow and its tint (`error` vs `secondary`), and the icon has a real `contentDescription` because it is no longer decorative.
       - **And the sequel, which is the more interesting half:** wiring the arrow to state produced a *new* wrong claim on a first day. `deltaIsPositive` is `todaySeconds > yesterdaySeconds`, and any usage at all beats zero, so a fresh install rendered a red upward arrow beside "No data for yesterday" — a direction against a baseline that doesn't exist. Caught on an emulator screenshot, not by a test. `deltaHasBaseline` now gates the icon, and the answer was to draw **no arrow**, not to pick a default: **a two-state field cannot express "there is nothing to compare".** Same shape as the theme override's tri-state, where a two-position `Switch` made "follow system" unreachable.
    3. The **donut arcs** came from a `UsageCategory.durationWeight()` table returning the mockup's literal 72/45/32 keyed off the *palette slot*, so every slice was drawn at a constant proportion regardless of the duration printed beside it in the legend. `UsageCategory` now carries `seconds` alongside its formatted `duration`, and `DonutChart` normalises those directly. **A formatted string is not a value** — any component that has to size something needs the number, not the label.
  - The empty "Recent Achievements" heading is likewise hidden rather than rendered over blank space — a bare heading reads as content that failed to load.
  - **Chart and trend must agree on what "this week" means.** Both now use the Mon–Sun calendar week; the trend previously summed rolling 7-day windows, so on a Monday it counted days the chart didn't draw and reported a rise next to a visibly flat week.
- **Settings persistence.** `SettingsRepository` (Preferences DataStore) persists the dark-mode override, cat-detection sensitivity, display name, daily-summary toggle, earned-minutes-per-cat, photo retention window, warning threshold, and reminder interval. `SettingsViewModel` wires flows only; the shaping lives in the pure `toSettingsUiState`/label functions in `SettingsMapper`. **`SettingsUiState.sample()` is `@Preview`-only** — production builds the state directly from real defaults (it used to be `sample().copy(...)`, which shipped mockup copy as the source of truth).
  - **Arity:** both `combine` calls in `SettingsViewModel` are at the typed five-flow limit. A new setting goes into the private `SettingsValues` holder or a sibling holder — never as a sixth top-level argument.
  - **Theme is special:** it lives in `UnPawseApp` so it can drive the whole app. `ThemeMode` (`ui/theme/ThemeMode.kt`) is the tri-state the user picks; the persisted form is still a nullable `Boolean` where absent means "follow system", and `setDarkModeOverride(null)` is what clears it. A two-position `Switch` could only ever write `true`/`false`, so the follow-system state was unreachable once touched.
  - **Settings that other components read** are exposed as `StateFlow`s on `AppContainer` — `catDetectorMinConfidence`, `earnedMinutesPerCat`, `warningMinutes`, `reminderMinutes` — and consumed as `() -> T` lambdas. That keeps DataStore out of `UsageTracker`/`CatDetector`/`CameraViewModel` and means a change takes effect on the next tick or capture without rebuilding anything.
    - **These four must NOT be `by lazy`** — every other container property is, so this is the one deliberate exception and it is load-bearing. `stateIn` seeds the flow with the *default* and swaps in the persisted value only once DataStore's first emission lands. Each of these is consumed by a lambda whose **first invocation is the decision itself**, so with `by lazy` the flow is created at that instant and `.value`, read microseconds later in the same expression, is always the default. Reproduced on-device: the camera granted 15 minutes instead of the user's configured 10 (and 20), and judged the first photo of every process against the 0.7 default gate instead of their sensitivity setting — logged `gate=0.7` on the first capture, `gate=0.5` on the second. Initialising eagerly starts collection in `Application.onCreate`, well ahead of any UI, including the cold launch-into-camera path from the block overlay. A new settings mirror added here must follow suit.
  - **The container also owns `DailySummaryWorker` scheduling**, collecting `dailySummaryEnabled` and scheduling/cancelling. Doing it there rather than in the ViewModel keeps the schedule correct for a process that never opens Settings.
- **Camera / detection.** `CameraViewModel` runs the pipeline *take photo → classify → save-if-cat*; the CameraX controller stays lifecycle-bound in the composable (`CameraRoute` passes a suspend capture lambda in). `CameraEvent` (`Saved` / `NotACat` / `Error`) is a one-shot `Channel`; `CameraRoute` acts on exactly one thing — dismissing the block overlay when a capture actually earned time (see the reward loop below) — because everything else already surfaces through the hint text. `CatDetector` wraps all ML behind one class; `classify` is a pure gate. Captures persist as app-internal JPEGs via `PhotoStorage` (no media permission).
- **Foreground detection & enforcement (`service/`).** `ForegroundAppMonitor` is the interface; `UsageStatsForegroundAppMonitor` polls `UsageStatsManager.queryEvents` every ~1s, querying only events *since the last tick* and remembering the last resumed package (so sitting still in one app keeps reporting it). It emits `null` when the screen is off — without that, the last app would accrue time all night. `UsageTracker` credits the interval *between* ticks to whichever app was in front, gated on `isMonitoredAndEnabled` so unmonitored apps never get a `daily_usage` row, and clamps each tick (`accrualMillis`, max 5s) so a doze/suspend gap can't silently burn a whole budget. It emits `limitReached` **once per breach** (not per tick), re-arming when the user switches away or earns time back. `UsageMonitorService` is a `specialUse` foreground service (required: tracking must survive backgrounding — exactly when the watched app is in front) started via `UsageMonitorController.startIfPermitted`. `UsageAccess` wraps the `PACKAGE_USAGE_STATS` app-op: **no runtime dialog exists**, so the Settings row deep-links to system Settings and the state is re-read on resume (`LifecycleResumeEffect` in the Settings destination, for the permission chips only).

- **Blocking schedules ("when", as opposed to a budget's "how much").** A `ScheduleWindow` (`data/schedule/`) is a recurring wall-clock window — start and end as minutes since local midnight, plus a days bitmask — that blocks apps outright, whatever budget is left. `packageName == null` makes it global (every monitored app); otherwise it is scoped to one. The whole rule lives in pure functions in `ScheduleMath.kt`, mirroring `UsageMath.kt`; `ScheduleGate` (`service/`) supplies only the clock, shaped like `FocusSession` and fed by an **eager** `scheduleWindows` mirror on `AppContainer` (same non-lazy reasoning as the settings mirrors — its first read *is* a blocking decision).
  - **A window whose end is at or before its start wraps past midnight, and the days mask then names the day it *starts* on.** "Bedtime 22:00–07:00, Fri" therefore runs Friday 22:00 to Saturday 07:00, which is what someone picking "Friday night" means; the tail after midnight is matched by testing the *previous* day against the mask. `start == end` falls out of the same branch as a full 24 hours, which is the only sensible reading of "from 08:00 until 08:00".
  - **Precedence is FOCUS > SCHEDULE > LIMIT**, decided in `UsageTracker`. It runs from most deliberate to least, and the first two are both escape-less — so when a window and a spent budget coincide the user gets the schedule overlay with **no camera button**. Offering it would be a promise the app can't keep: earned minutes raise a *budget*, and no amount of budget makes it not be bedtime. `BlockEvent` carries the window's `endsAtMinuteOfDay` so the overlay can say what the block is until without re-reading the schedule.
  - **`UsageTracker.blockReleased` is how the overlay comes down without an app switch.** A focus session has an end time the service can `delay` on; a window just stops covering the current minute. Rather than add an alarm, the tracker — already evaluating every tick — emits the package when *every* block reason has cleared, and the service hides the overlay if it matches. Not schedule-specific: it also lifts a limit block the moment earned time puts the app back in budget. Boundaries are therefore **best-effort within one poll interval** while the service is alive; nothing wakes the device at a window's edge.
- **Weekday/weekend budgets.** `monitored_apps.weekendLimitMinutes` is a nullable override: `null` follows `dailyLimitMinutes`, a positive value is a separate Saturday/Sunday budget, and `UNLIMITED_MINUTES` means no cap (so "weekday-only limits" is expressible). **The sentinel is negative, not zero** — a limit of 0 already means "over budget from the first second" throughout the enforcement path and several tracker tests rely on it, so overloading zero would have flipped them from "blocked instantly" to "never blocked". `effectiveLimitMinutes` resolves the split against the same `today()` the usage row is keyed by. `remainingMinutes` returns **null on an uncapped day**, which the warning path already treats as "nothing to warn about"; `UsageRepository.setLimit` carries an existing override across so the monitor switch and the limit stepper can't silently reset it.
- **`daily_usage.blockedCount` records blocks raised**, one per breach, and is what Stats' "Prevented" card reports. Written from **`UsageTracker`, on the line after `_blockRequired.emit`** — not from `UsageMonitorService.observeBlockRequired`, which is where the overlay actually goes up. The tracker branch already owns the once-per-breach `signalledFor` de-dup and already holds the repository, so the stored count is provably the same set of events as the flow; putting it in the service would add a `SharedFlow` hop and move it into Context-bound, device-verified-only territory. The service is the only consumer and never filters an event out, so the two sites are semantically equivalent.
  - **A block row rather than a `block_events` table**: a block is a per-app, per-day fact keyed exactly like usage, so the composite key already gives it free daily reset and the `@Transaction` insert-then-increment already gives it atomicity — and Stats' existing `observeRecentUsage(14)` already loads it, so no new flow and no pressure on the combine arity. An event table would buy time-of-day analysis nothing asks for, at the cost of unbounded growth plus a `CaptureRetentionWorker`-style purge.
  - **Counting semantics:** `signalledFor` re-arms on an app switch, so leaving a blocked app and returning counts as a **second** prevented interruption. That is deliberate — it is a second time the user was stopped — so don't "fix" it into once-per-day. All three reasons count: a focus session and a schedule window prevent an interruption just as a spent budget does.
- **`monitored_apps.category` is carried across by the same rule.** The column is a nullable `AppCategory.name` — nullable so "nobody has classified this" stays distinguishable from a deliberate choice of `OTHER`, though both render as Other. `setLimit`'s `defaultCategory` parameter only ever **seeds a row that doesn't exist yet** (the platform's guess at first enable) and never overwrites a stored value, because the picker passes it on every stepper nudge too; without that rule a limit change would silently undo the user's category choice. `MonitoredApp.category` is non-null — the null is resolved in `toDomain()` so no consumer handles it.
- **Starting the monitor is `startIfPermitted`'s job alone, called from several triggers — never inline a start elsewhere.** It is the single gate and is idempotent + self-refusing: it no-ops without usage access, and it **catches `ForegroundServiceStartNotAllowedException`** (an `IllegalStateException`, so no `SDK_INT` branch) and returns `false` rather than crashing when the platform forbids a background FGS start (API 31+). Triggers, in order of coverage: (1) an app-wide `LifecycleResumeEffect(Unit)` in `UnPawseApp` — fires on **every** resume regardless of tab, so returning from the usage-access screen to *any* screen starts it (the original bug was that only the Settings tab did); (2) `UnPawseApplication.onCreate()` — covers cold starts that never resume the UI (launch-into-camera from the block, a `START_STICKY` revival); (3) `BootReceiver` on `BOOT_COMPLETED` — covers reboots; (4) `MonitorHealthWorker`, a 15-minute periodic `WorkManager` job scheduled from `onCreate` (`KEEP` policy, so it neither duplicates nor resets) — the self-heal for when `START_STICKY` and the receiver are both defeated by an OEM battery manager, so monitoring recovers within a period instead of staying dark. All four route through the one gate and add no logic of their own; a killed/rate-limited trigger self-heals on the next one.
  - **Why the catch is not defensive paranoia:** on a real reboot, `Application.onCreate()` runs *before* the broadcast reaches the receiver, in `uidState: CEM` with no boot allowlist, so its start genuinely throws — verified on an API-36 emulator, where the catch swallowed it 10 ms before `BootReceiver` (now in `uidState: RCVR`, holding the 20 s `reasonCode:BOOT_COMPLETED` temp-allowlist) started the service into the foreground. Without the catch the app would crash in `onCreate` on **every** boot.
- **The block overlay (`BlockOverlayHost`/`BlockOverlayController`).** When `limitReached` fires, the service draws `BlockOverlayScreen` in a `TYPE_APPLICATION_OVERLAY` window over the offending app (needs `SYSTEM_ALERT_WINDOW`, which also grants the background activity launch used by "Open Camera"). The window is intentionally **touchable and focusable** — it must swallow input to the app underneath. Compose normally inherits its lifecycle/saved-state/ViewModel owners from an Activity; there is none here, so `BlockOverlayHost` *is* those owners. Hosts are **single-use** (a `LifecycleRegistry` can't return from `DESTROYED`), so the controller builds a fresh one per show. All of it is **main-thread only** (`WindowManager.addView`), hence the `withContext(Dispatchers.Main)` in the service.
  - **Gotcha:** anything rendered in this window runs *outside an Activity*. `UnPawseTheme` therefore casts with `view.context as? Activity` — an unconditional cast crashed the app with `ClassCastException: UnPawseApplication cannot be cast to Activity` the first time the block fired. Keep Activity assumptions out of composables that the overlay can reach.
  - Both overlay buttons must dismiss first: the overlay sits above *every* app including our own, so leaving it up would cover the camera. "Exit App" goes home rather than back into the blocked app; returning re-triggers the block anyway, so the limit holds.
  - An overlay window **outlives app switches by design**, so the service also hides it whenever the foreground moves off the blocked app (`dismissBlockWhenUserLeaves`). Without that, a home gesture strands the block on top of the launcher. The tracker republishes the foreground app as a `StateFlow` for this — don't collect `ForegroundAppMonitor.foregroundApp()` again, it's a cold flow and would start a second poller.
- **The reward loop.** `BlockSession` is the thread between the block and the camera: the service arms it with an `ArmedBlock` (id + package + `armedAtMillis`) when raising the overlay, and `CameraViewModel.creditBlockedApp` settles it when ML Kit confirms a cat. **No explicit "unblock" step exists**: crediting lifts the budget above what's been used, so `isLimitReached` goes false and the tracker simply stops signalling. The session deliberately outlives the overlay (the debt survives "Open Camera" taking the block down) but is cleared by "Exit App". `CameraEvent.Saved` carries a `RewardOutcome` so the hint can say what the cat was worth; crediting is ViewModel work, while `CameraRoute` takes down the overlay (a window this side owns) **only on `RewardOutcome.Earned`** — leaving it up after a refusal, since the app is still blocked.
  - **The escape hatch is bounded, and the bounds are the point.** It used to have no floor: a block re-arms the moment the granted minutes are spent, so photo → 15 min → photo → 15 min repeated forever and a static cat photo on a second screen defeated the daily limit entirely. Three independent bounds now apply, each with its own reason for living where it does:
    1. **A 5-minute redemption window** (`BLOCK_REDEEM_WINDOW_MINUTES`). `BlockSession.current()` returns the armed block only inside it and clears a lapsed one on read — lazy and self-healing, because nothing needs to *react* to a window closing and a coroutine per block would be state to leak. This closes the back door left by `dismissBlockWhenUserLeaves`, which hides the overlay without clearing the debt: without a window, a session armed this morning was still redeemable tonight by a casual capture from the Camera *tab*. **Not persisted, unlike `FocusSession`** — five minutes spanning a process death isn't worth a DataStore key plus a container collector, since the overlay is gone too and returning to the app re-arms within a tracker tick.
    2. **A per-app daily cap** (`DAILY_EARNED_CAP_MINUTES`, 60 — four cats at the shipped grant). Needed **no schema change**: `earnedSeconds` is only ever incremented, so today's value *is* today's cumulative grant total, and `(packageName, date)` already resets it at midnight. A grant is trimmed to whatever is left of the cap rather than refused outright, so `earnedSeconds` never passes it and the last cat of the day still buys something.
    3. **A per-app cooldown** (`REWARD_COOLDOWN_MINUTES`, 10), stamped into `daily_usage.lastEarnedAtMillis` by the same `@Transaction` that increments `earnedSeconds`. **Persisted precisely because the session isn't**: it is the defence against the fast loop, so it must not be resettable by force-stopping the app. A backstop rather than the primary bound — at the 15-minute grant it never bites; it bites at small grant settings, where a 5-minute reward could otherwise be re-earned every 5 minutes.
  - **`UsageRepository.tryEarnMinutes` is the only sanctioned credit path** — it applies all of the above and returns a `RewardDecision`. `addEarnedMinutes` remains the uncapped primitive for seeding and tests; calling it from the reward loop bypasses the cap silently. The decision logic is pure and top-level in `data/usage/RewardPolicy.kt`, beside `UsageMath.kt` and for the same reason. **The cap is reported ahead of the cooldown** when both apply: waiting out a cooldown that ends in a refusal is worse advice than "you're done for today".
  - **A refusal the user can't explain reads as the app being broken**, so each outcome says something different. `RewardOutcome` (`NoActiveBlock` / `Earned` / `DailyCapReached` / `CoolingDown`) drives `savedHint` in `ui/camera/CameraHints.kt` — pure top-level functions, like `warningText`, so the copy is unit-tested. And when an app has spent its allowance the overlay uses `BlockUiState.forAppOutOfRewards` (`showCamera = false`, reusing the affordance built for focus mode) and the service **does not arm a session at all**: offering an escape that would refuse the photo is worse than offering none.
  - **A capture records what it was worth** (`CaptureEntity.earnedMinutes`, 0 when it bought nothing), written by a follow-up `recordEarnedMinutes` after the credit rather than as a `saveCapture` parameter — the photo is stored *before* the credit is attempted, so a crediting failure can't cost the user their photo, and a row that never gets updated reads as "earned nothing", which is true. It has to be stored because nothing can reconstruct it: `daily_usage` holds a running per-app total with no link back to the photo. Home's Recent Activity previously asserted `"Time earned back."` for **every** cat, so spamming the shutter on a fresh day looked like it was working; it now reports `earnedMinutes` or says only that the photo was saved. Same rule as the Stats note above — don't state a number the app didn't compute.
  - Verified cats are **still saved when they earn nothing** (and still count toward the Home "Cats" pill and the streak): unPawse is a cat-photo app, the gallery and the streak are about photographing a cat daily, and neither claims anything about rewards. The bounds limit what a photo can *buy*, not whether it can be taken.
  - Reward captures keep **`isBonus = false`** — that flag means a *streak* bonus in the Gallery (blush card, "Daily streak bonus!", no AI badge). An unblock capture is an ordinary verified cat.
- **App picker + package visibility.** `InstalledAppsProvider` (`data/apps/`) fences off `PackageManager` so ViewModels stay testable. It queries **only LAUNCHER-resolvable apps**, which is the deliberate, restrained answer to Android 11+ package visibility: it needs the `<queries>` intent element in the manifest but **not** `QUERY_ALL_PACKAGES` (which triggers Play Store sensitive-permission review). Consequence: non-launchable apps never appear in the picker — fine, since you can't spend screen time in an app you can't open.
  - **App categories** (`data/usage/AppCategory.kt`: SOCIAL / PRODUCTIVITY / ENTERTAINMENT / OTHER) come from `ApplicationInfo.category`, read off the `ResolveInfo` the picker query **already returns** — no second `PackageManager` call, no extra flags, and **no new permission**, since it's only ever read for apps that are launchable and therefore already visible to us. `categoryFromPlatform` is pure and top-level so the whole map is tested without a device.
  - **The map is deliberately conservative.** Only `CATEGORY_SOCIAL`, `CATEGORY_PRODUCTIVITY` and the four media categories (`GAME`/`AUDIO`/`VIDEO`/`IMAGE`) map. `CATEGORY_NEWS` and `CATEGORY_MAPS` map to `null`, as does anything from a newer platform. The field is declared by each app's *own* developer and is frequently absent, so forcing a news reader into "Entertainment" would be unPawse asserting something it doesn't know — the same failure the Stats blanking rule exists to prevent. Everything unmapped shows as **Other**, which is a real bucket rather than a hole, and the user corrects it in one tap. App **icons are loaded lazily per visible row** (`ui/apppicker/AppIcon.kt`, `produceState` + IO) rather than eagerly for every app, keeping `Drawable`s out of UI state and off the main thread.
- **Navigation:** single-activity, `navigation-compose` with **plain string routes** (`Routes`), deliberately **not** kotlinx-serialization type-safe routes (avoids a second compiler-plugin/version-matching dependency). Tabs use `popUpTo(start){saveState}; launchSingleTop; restoreState`. Settings rows emit ids (`SettingsRowIds`); `SettingsRoute` — not the NavHost — maps them to a destination or a system intent, so the navigation graph knows nothing about Settings' internals. **Every declared id now leads somewhere**; the `when` has an explicit `else` so a future unhandled id is a visible gap rather than a silent fall-through. The **Block Overlay** is a normal destination (no bottom bar) temporarily reachable from Home's "Pause Protection" card — this stays as a debug/preview entry; the real limit-reached trigger is being built (see Open Decisions + roadmap).
- **Theme:** `UnPawseTheme(darkTheme, content)` maps all `DESIGN.md` tokens to a `lightColorScheme`; no dynamic color (blush-pink brand identity is intentional). The **dark scheme is provisional** (derived from fixed/inverse tokens) — refine against a real dark mockup.
- **Typography:** the type scale matches `DESIGN.md`, but the family is currently the **platform sans-serif**, not Inter. To switch to Inter: drop the four OFL TTFs into `res/font/` and replace `AppFontFamily` in `ui/theme/Type.kt`.
- **Icons:** `material-icons-extended` — the ~40 mockup symbols map nearly 1:1; R8 strips the unused ones. Notable substitutes: `Shield` (Pause Protection), `GridView` (Gallery), `LocalCafe`, `PhoneAndroid`.
- **Insets:** `enableEdgeToEdge()`; `Scaffold` inner padding is applied as lazy-list `contentPadding` so content scrolls under the bars; Camera consumes only the status-bar inset; Block uses `safeDrawingPadding()`.
- Add new dependencies via the version catalog and reference them as `libs.*`. Package everything under `com.example.unpawse`.

### Resolved
- **App categories: a column on `monitored_apps`, not a separate table.** Resolved with the user: auto-guess from `ApplicationInfo.category` with a user override in the App Picker, rather than platform-only (a large unfixable "Other" slice, since the field is developer-declared and often absent) or user-only (the donut stays one grey blob until they do the work). Stored as a nullable `String` holding an `AppCategory.name` — no `TypeConverter`, survives a reorder of the enum, and reads correctly in the `sqlite3` dumps the emulator checks use.
  - **Known trade-off:** `daily_usage` rows outlive `removeMonitoredApp`, so an orphaned row has neither a label nor a category. It doesn't bite today — the breakdown filters to enabled apps and to *today* — but a future usage-history view would show those hours as Other. A separate `app_categories` table surviving removal would fix that, at the cost of a table, a join and a purge-lifecycle question, for a screen that doesn't exist.
- **Scheduled blocking and day-varying budgets.** Resolved with the user before implementation:
  - **Both global and per-app windows**, so "bedtime" is set once rather than repeated per app, without giving up finer control.
  - **Weekday/weekend split, not full Mon–Sun.** One nullable override covers the case people actually have ("30m on school nights, no cap Saturday"); seven independent values would have meant a much busier row for a case nobody asked for.
  - **A scheduled block is escape-less**, like focus. Earned minutes raise a budget, so they logically cannot unlock a rule about *when* — the overlay hides the camera button rather than offering an escape it would then refuse.
  - **Best-effort boundaries on the existing ~1s tracker tick**, no `AlarmManager`. An exact alarm plus a heads-up warning was considered and deferred: it adds OEM-doze caveats and a second scheduling mechanism, and the tick already blocks within a second of the user actually being in a covered app. Recorded as a known gap.
- **Settings build-out (all rows).** Resolved with the user, one function per phase:
  - **Daily limit** → a read-only *derived* total of the enabled per-app limits ("4h 15m across 5 apps"), retitled "Total daily limit". unPawse enforces per-app limits only; a global cap would have meant new enforcement in `UsageTracker`, and the old title read as one.
  - **Break duration** → repurposed as **"Time earned per cat"**, the control for `BONUS_MINUTES_PER_CAT`. No break feature exists anywhere in the app, so the row described nothing; the reward grant was a real number that happened to be hardwired.
  - **Confidence threshold** and **Require live photo** → **removed**. The first contradicted the sensitivity slider directly above it (the slider *is* what sets the gate); the second persisted to DataStore with no consumer and nothing to gate, since there is no photo-import path.
  - **Delete history** → a **full reset** (usage, limits, photos, preferences, plus the in-memory focus/block sessions), retitled "Delete all data" and gated behind a dialog that enumerates the loss. The monitor service is deliberately *not* stopped: with no monitored apps it accrues and blocks nothing, and a stop/restart would add a platform-refusable FGS start for no gain.
  - **Export** → JSON via the system file picker (SAF `CreateDocument`), so no storage permission is involved. Captures export as **metadata only** — no bytes, no file paths, which would leak the private-storage layout into a file the user may share.
  - **Privacy policy** → an in-app screen, not a link. There is no hosted policy, and an app with no `INTERNET` permission cannot fetch one anyway.
  - **Theme** → tri-state System/Light/Dark (see the Settings persistence note).
  - **Notifications** → all three built, behind a real `POST_NOTIFICATIONS` request. The pre-lock warning fires from `UsageTracker`; the recap is a WorkManager job; the reminder is an in-service ticker, chosen because WorkManager's 15-minute floor can't express the shorter intervals and a reminder only makes sense while the user is in a limited app — exactly when the service is already awake.
- **Foreground-app detection: `UsageStatsManager` polling** (not `AccessibilityService`). A foreground Service polls `queryEvents` ~1s. Cost: `PACKAGE_USAGE_STATS` (granted via a Settings redirect, not a runtime dialog), a foreground service + persistent notification, ~1–2s block latency, and `SYSTEM_ALERT_WINDOW` to draw the block over the offending app. **Why not AccessibilityService:** it would be near-instant, notification-free, and could redirect without an overlay permission — but Play Store review rejects most non-accessibility uses of it, it can read screen content (privacy scrutiny), and the permission ask is far heavier. The latency and notification are an acceptable price for a shippable app. `ForegroundAppMonitor` is an interface, so an Accessibility implementation could be slotted in later without touching callers.

- **Data/persistence:** **Room** for structured/relational data (captures; per-app limits + usage next) and **Preferences DataStore** for scalar settings. (No remote API.)
- **Camera/detection:** **implemented** — CameraX capture + ML Kit on-device cat verification behind `CatDetector`.

- **Restart monitoring after reboot: a `BOOT_COMPLETED` `BootReceiver`** that only calls `UsageMonitorController.startIfPermitted` (no start/stop logic of its own). **`BOOT_COMPLETED` only, deliberately not `LOCKED_BOOT_COMPLETED`:** the latter is delivered solely to `android:directBootAware` components, and ours can't be — the Room DB and settings DataStore both live in credential-protected storage, unreadable until first unlock. Nothing is lost by waiting: a locked device can't run the apps we watch, so there's no screen time to track before the unlock that `BOOT_COMPLETED` already follows on FBE devices.
